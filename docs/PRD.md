## 1. 概述

### 1.1 背景

中医经典（伤寒论、神农本草经、黄帝内经等）知识体系庞大，条文间存在复杂的「方剂-药材-证型」关联网络。通用大模型在回答中医问题时存在三个短板：缺乏经典原文引用、不懂方剂间的药味加减关系、回答风格不像中医师。

本项目通过 **LoRA 微调 + GraphRAG 检索** 的组合方案，构建一个部署在 2 核 4G 服务器上的中医经典知识检索与理解助手。模型通过微调获得口语化讲解风格（不像教科书，像老师讲课），知识图谱提供精确的方药关联检索，向量库提供经典原文语义检索。

### 1.2 目标

| 优先级 | 目标 | 验收方式 |
|---|---|---|
| P0 | 跑通「PDF 提取 → SFT 数据 → LoRA 微调 → Ollama 部署」端到端流水线 | 全流程无人工干预跑通 |
| P0 | 跑通「经典原文 → 知识图谱 + 向量库 → GraphRAG 检索」 | 图谱查询 + 向量检索均可用 |
| P0 | 部署到 2 核 4G 服务器，可通过 Web 接口对话 | 响应延迟 < 60s/回答（流式） |
| P1 | 50 题评测集，P2 阶段正确率比 P0 baseline 提升 ≥ 15% | 评测报告量化对比 |
| P1 | LoRA 微调后回答具有口语化讲解风格（口语标记词密度 ≥ 基座 2 倍） | 对比 base 模型量化口语化指标 |
| P2 | GraphRAG 在方剂关联查询上准确率优于纯向量 RAG | 评测集分组对比 |
| P2 | 公众号一篇高质量开源介绍文章 | 可发布 |

### 1.3 范围

**包含：**

- 倪海厦讲稿 PDF 提取与 SFT 数据构建
- 伤寒论等经典原文的结构化与知识图谱构建
- Qwen2.5-1.5B-Instruct 的 LoRA 微调
- 向量 RAG（ChromaDB）+ 图谱 RAG（NetworkX）双路检索
- FastAPI Web 服务，流式输出
- 2 核 4G 服务器部署
- 50 题评测集与三阶段（P0/P1/P2）效果对比
- 公众号开源介绍文章

**不包含：**

- 在线问诊或医疗建议（产品定位是经典知识检索与理解，不是诊疗工具）
- 多用户平台化（单用户部署）
- 模型蒸馏算法研究（用成熟 LoRA，不研究新算法）
- 持续公众号运营（只写一篇高质量文章）

### 1.4 术语表

| 术语 | 说明 |
|---|---|
| LoRA | Low-Rank Adaptation，低秩适配器微调。只训练少量适配器参数，基座冻结 |
| GraphRAG | 基于知识图谱的检索增强生成，利用图结构做多跳关联查询 |
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| SFT | Supervised Fine-Tuning，监督微调 |
| Q4 量化 | 4-bit 量化，模型体积约为原版 1/4，精度损失小 |
| Ollama | 本地大模型运行工具，支持 GGUF 量化模型 |
| ChromaDB | 轻量向量数据库，支持嵌入式部署 |
| NetworkX | Python 图分析库，内存中存储知识图谱 |
| 伤寒论 | 张仲景所著中医经典，含 397 条辨、113 首方剂 |
| 方剂 | 中医处方，由多味药材按特定比例组成 |
| 证型 | 中医辨证分型，如太阳病、阳明病 |
| 条辨 | 伤寒论中的条文编号 |

## 2. 产品定位

### 2.1 目标用户

- **主要用户**：Apex 本人及导师（练手项目，受众极小）
- **技术背景**：了解 AI 编程工具，熟悉 Git/Python，对中医有学习兴趣
- **设备**：2 核 4G 云服务器 + 个人 PC

### 2.2 核心场景

用户在 Web 界面输入中医问题，系统经过「查询路由 → 向量检索 + 图谱查询 → 拼接上下文 → LoRA 模型生成」的流程，返回带有经典原文引用和方药关联信息的回答，风格类似倪海厦医师的讲解。

**典型问答示例：**

> **用户**：桂枝汤的组成是什么？和麻黄汤有什么区别？
>
> **助手**：桂枝汤由桂枝、芍药、甘草、生姜、大枣五味药组成，是太阳中风证的主方。麻黄汤呢，由麻黄、桂枝、甘草、杏仁四味药组成，治的是太阳伤寒证。两方的共同药物是桂枝和甘草——桂枝解肌发汗，甘草和中。区别在于：桂枝汤用芍药敛阴，配上生姜大枣调和营卫；麻黄汤用麻黄杏仁开腠理、降肺气。一个走和法，一个走汗法，方向不同。

### 2.3 能力边界

| 能做 | 不做 |
|------|------|
| 检索经典原文并解释含义 | 诊断具体病人的病情 |
| 查询方剂组成、加减变化、药味差异 | 开处方或给用药建议 |
| 多跳关联查询（药→方→证） | 替代中医师的专业判断 |
| 用口语化风格讲解中医知识 | 回答与中医无关的问题 |
| 量化对比 RAG vs GraphRAG 效果 | 追求 SOTA 学术指标 |

## 3. 技术选型

### 3.1 选型决策

| 维度 | 决策 | 理由 |
|------|------|------|
| 技术路线 | 路线③ LoRA + GraphRAG | 中医知识是关系型网络，图检索优于纯向量；有技术深度和创新性 |
| 基座模型 | Qwen2.5-1.5B-Instruct | 2 核 4G 可跑 Q4 量化（~1.2GB）；仲景项目已验证 1.8B 可行 |
| 微调方法 | LoRA（先跑通，数据够再考虑全参） | 1.5B 模型小，LoRA 成本低可迭代 |
| 推理方案 | 本地 Ollama 推理 | 体现端侧主题，零 API 成本 |
| 向量库 | ChromaDB | 轻量，2 核 4G 够用，嵌入式无需独立进程 |
| Embedding | bge-small-zh-v1.5 | 中文检索好，体积小（~100MB） |
| 图谱引擎 | NetworkX 内存图 | Neo4j 太重（JVM 1.5GB），NetworkX 够用 |
| Web 框架 | FastAPI + 轻量前端 | 异步支持，流式输出 |
| 依赖管理 | uv | 快速、可复现 |

### 3.2 关键依据

- **GitHub 调研**：仲景(ZhongJingGPT) 用 Qwen1.5-1.8B 微调 13.5 万条中医指令，T4 可推理
- **学术研究**：RAG > FT only，FT+RAG 最优；MedGraphRAG 是医学 QA 当前 SOTA
- **可行性验证**：PDF 提取 17/17 关键词命中（0.05% 乱码）；图谱查询 0.01ms（详见 feasibility-report.md）

### 4.1 数据源

| 来源 | 内容 | 获取方式 | 验证状态 |
|------|------|---------|---------|
| qhsxzh.com | 人纪系列 5 本 PDF（针灸/内经/本草/伤寒/金匮） | 直接下载 | 已验证，文本型 PDF |
| 维基文库 | 伤寒论原文（公版） | WebFetch | 已获取 |
| nihaixia.org | 完整资料包 13 文件 | 百度网盘(提取码 7p8t) | 已确认 |
| jingfangzhijia.cn | 倪海厦医案电子版 | 网页 | 待验证 |

### 4.2 数据分流

| 数据类型 | 去向 | 处理方式 | 理由 |
|---------|------|---------|------|
| 倪海厦讲稿/对话 | SFT 训练集 | PDF 提取 → 清洗 → 指令格式化 | 口语化黄金数据，学口语化表达方式 |
| 经典原文（伤寒论等） | RAG 向量库 + 知识图谱 | 结构化抽取 → 分块向量化 + 三元组抽取 | 公版，结构化，适合检索引用 |
| 方剂-药材-证型关系 | 知识图谱 | 半自动抽取 → 人工校验 → NetworkX | 关系型数据，图谱查询最优 |
| 倪注教材 | 训练辅助 + RAG 参考 | 按质量分流 | 讲稿质量 > 教材，优先用讲稿 |

### 4.3 SFT 数据格式

```json
{
  "instruction": "请解释桂枝汤的组成和主治。",
  "input": "",
  "output": "桂枝汤是伤寒论第一方，由桂枝三两、芍药三两、甘草二两、生姜三两、大枣十二枚组成。这个方子治的是太阳中风证——什么意思呢，就是你受了风邪，营卫不和，出现头痛、发热、汗出、恶风这些症状。桂枝解肌发汗，芍药敛阴和营，一散一收，调和营卫。配上甘草和中，生姜散寒，大枣补虚。这个方子看起来简单，但配伍非常精妙……"
}
```

**格式要求：**
- instruction 为中医知识问题
- output 保留口语化讲解风格（「什么意思呢」「你想想看」等口语表达）
- 长度控制在 200-800 字，适合 1.5B 模型的生成能力
- 避免涉及具体诊疗建议

## 5. 功能需求

### FR1：PDF 提取与文本清洗

**输入**：qhsxzh.com 下载的 5 本 PDF（针灸/内经/本草/伤寒/金匮）

**处理流程：**

| 步骤 | 说明 | 工具 |
|------|------|------|
| 1. 下载 | 批量下载 5 本 PDF | requests |
| 2. 提取 | PyMuPDF 提取文本（已验证质量最佳） | fitz |
| 3. 去噪 | 去除页眉页脚、水印、公众号推广信息 | 正则 |
| 4. 分章 | 按条辨/方剂/章节切分 | 规则 + 正则 |
| 5. 质量报告 | 统计提取率、关键词命中、乱码率 | 自动 |

**验收标准**：
- 5 本 PDF 全部提取成功
- 关键词命中率 ≥ 95%
- 乱码率 < 1%
- 产出 `cleaning_report.json` 含每本书的质量指标

### FR2：SFT 训练数据构建

**输入**：FR1 产出的清洗文本

**处理流程：**

| 步骤 | 说明 |
|------|------|
| 1. 段落切分 | 按讲稿的自然段落/条辨切分 |
| 2. 指令生成 | 用 GPT/规则将讲稿内容转为 instruction-output 对 |
| 3. 质量过滤 | 丢弃过短（<50 字）、重复、含敏感信息的样本 |
| 4. 去重 | 语义去重，避免高度相似样本 |
| 5. 格式化 | 转为 Alpaca/ShareGPT 格式 JSONL |

**验收标准**：
- 产出 `train.jsonl`，预估 5000-15000 条
- 每条含 instruction + output，output 保留口语化风格
- 含数据统计报告（条数、平均长度、token 估算）

### FR3：知识图谱构建

**输入**：伤寒论原文 + 倪注方剂表

**图谱 schema：**

```
节点类型：
  - Formula（方剂）：{name, source, indication}
  - Herb（药材）：{name, nature}  # 寒热温凉
  - Syndrome（证型）：{name, description}
  - Text（条文）：{number, content}

边类型：
  - CONTAINS（方剂→药材）：{dosage}  # 如 桂枝汤 -CONTAINS-> 桂枝(三两)
  - TREATS（方剂→证型）：{}  # 如 桂枝汤 -TREATS-> 太阳中风证
  - DERIVED_FROM（方剂→方剂）：{change}  # 如 桂枝加葛根汤 -DERIVED_FROM-> 桂枝汤(+葛根)
  - MENTIONS（条文→方剂）：{}  # 如 第12条 -MENTIONS-> 桂枝汤
```

**构建流程：**

| 步骤 | 说明 | 方式 |
|------|------|------|
| 1. 方剂-药材关系 | 113 首方剂的组成 | 半自动抽取 + 人工校验 |
| 2. 方剂-证型关系 | 方剂主治证型 | 伤寒论原文 + 倪注 |
| 3. 方剂加减关系 | 方剂间的加减变化 | 伤寒论条文提取 |
| 4. 条文-方剂关系 | 条文与方剂的引用 | 条文编号映射 |
| 5. 持久化 | 导出 JSON，支持加载重建 | NetworkX node_link_data |

**验收标准**：
- 图谱节点 ≥ 200（含 113 方剂 + ~80 药材 + ~30 证型）
- 图谱边 ≥ 500
- 支持多跳查询：方剂→药材、方剂→证型、方剂→加减方
- JSON 持久化加载 < 100ms
- 产出 `graph_stats.json` 含图谱统计

### FR4：LoRA 微调

**基座模型**：Qwen2.5-1.5B-Instruct

**训练环境**：AutoDL A100 40G（或 3090 24G）

**关键超参：**

| 参数 | 值 | 说明 |
|------|-----|------|
| method | LoRA | 低秩适配器 |
| lora_rank | 8 | 低秩维度 |
| lora_alpha | 32 | 缩放系数 |
| lora_dropout | 0.05 | 防过拟合 |
| target_modules | q_proj, v_proj | 注意力层 |
| learning_rate | 2e-4 | LoRA 用较大学习率 |
| epochs | 3 | 小模型多跑几轮 |
| batch_size | 8 | |
| gradient_accumulation | 4 | 等效 batch 32 |
| max_seq_len | 1024 | 覆盖多数中医问答 |
| warmup_ratio | 0.03 | cosine schedule |
| precision | bf16 | 混合精度 |

**训练脚本要求：**
- 参数通过命令行或 config 文件传入，不硬编码
- 支持 `--smoke-test` 模式：tiny 模型 + 10 条 + 1 step（供 CI 用）
- 训练日志、loss 曲线自动保存
- 训练完成自动保存 LoRA adapter 权重

**量化导出：**
- LoRA adapter 合并到基座 → `convert_hf_to_gguf.py` → `llama-quantize` Q4_K_M
- 量化后模型约 1.2 GB

### FR5：向量 RAG

**Embedding 模型**：bge-small-zh-v1.5

**文档库构建：**

| 步骤 | 说明 |
|------|------|
| 1. 分块 | 经典原文按条辨切分，每块 100-300 字 |
| 2. 向量化 | bge-small-zh 生成 embedding |
| 3. 入库 | ChromaDB 嵌入式存储 |
| 4. 索引 | 默认 HNSW 索引 |

**检索接口：**
```python
def vector_search(query: str, top_k: int = 5) -> list[Document]:
    """向量检索，返回 top_k 相关文档"""
```

**验收标准**：
- 伤寒论 397 条全部入库
- 检索延迟 < 50ms
- 关键条文检索 recall@5 ≥ 80%

### FR6：GraphRAG 查询

**查询接口：**

```python
def graph_query(question: str) -> GraphResult:
    """图谱查询，返回关联的方剂/药材/证型信息"""
    # 1. 实体识别（从问题中提取方剂名/药名/证型名）
    # 2. 多跳查询（方剂→药材、方剂→证型、方剂→加减方）
    # 3. 返回结构化结果
```

**支持的查询模式：**

| 模式 | 示例 |
|------|------|
| 方剂组成 | "桂枝汤有哪些药" → [桂枝, 芍药, 甘草, 生姜, 大枣] |
| 方剂对比 | "桂枝汤和麻黄汤的区别" → 共同药 + 差异药 |
| 药材反查 | "含甘草的方剂" → [桂枝汤, 麻黄汤, ...] |
| 多药材交集 | "同时含桂枝和麻黄的方剂" → [麻黄汤, 大青龙汤, ...] |
| 证型-方剂 | "太阳病用什么方" → [桂枝汤, 麻黄汤, ...] |
| 方剂加减 | "桂枝汤变桂枝加葛根汤加了什么" → +葛根 |

### FR7：查询路由与生成

**查询路由逻辑：**

```
用户问题
  │
  ├─ 含方剂名/药名/证型名？ ──→ GraphRAG 查询 + 向量检索
  │
  ├─ 纯文本解释类？ ──→ 向量检索 only
  │
  └─ 闲聊/无关？ ──→ 直接生成（拒绝或引导）
```

**生成流程：**

1. 查询路由判断需要哪些检索
2. 向量检索 top_k 经典原文片段
3. 图谱查询关联的方药信息
4. 拼接 system prompt + 检索上下文 + 用户问题
5. Ollama 流式生成回答

**System Prompt 模板：**

```
你是一位中医老师，擅长用通俗易懂的方式讲解中医经典知识。
请根据提供的经典原文和方药信息回答问题。

注意事项：
- 引用经典原文时标注条文编号
- 解释方剂时列出完整组成
- 不提供具体诊疗建议
- 用口语化的讲解风格

[检索到的经典原文]
{retrieved_docs}

[图谱关联信息]
{graph_result}
```

### FR8：Web 服务

**技术栈**：FastAPI + SSE 流式输出 + 轻量前端

**API 设计：**

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/chat` | POST | 流式对话，SSE 返回 |
| `/api/health` | GET | 健康检查 |
| `/api/graph/stats` | GET | 图谱统计信息 |

**前端：**
- 单页面，输入框 + 对话气泡
- 流式逐字显示回答
- 回答中高亮方剂名、药名
- 显示检索到的原文引用（可折叠）

**并发控制：**
- 全局信号量锁，并发限制为 1
- 请求队列，超时返回 429

### FR9：评测体系

**评测集（50 题，Day 1 优先构建）：**

| 类别 | 题数 | 示例 |
|------|------|------|
| 经典原文检索 | 15 | "伤寒论第12条原文是什么" |
| 方剂查询 | 10 | "桂枝汤的组成" |
| 药材关联 | 10 | "同时含桂枝和麻黄的方剂" |
| 经典解释 | 10 | "什么是太阳中风证" |
| 综合问答 | 5 | "桂枝汤和麻黄汤在主治上的区别" |

**评测指标：**

| 指标 | 计算方式 | 目标 |
|------|---------|------|
| 检索 recall@5 | 正确文档出现在 top5 的比例 | ≥ 80% |
| 答案正确率 | 人工判断答案是否正确 | P2 ≥ 75% |
| 口语化程度 | 口语标记词密度（微调 vs 基座）、平均句长比、反问/感叹句比例 | 口语标记词密度 ≥ 基座 2 倍；平均句长 ≤ 基座 70% |

## 13. 模型能力边界与设计决策

### 13.1 背景

本项目基座模型为 Qwen2.5-1.5B-Instruct（Q4 量化，~1.2GB），部署在 2 核 4G 服务器上。该模型规模决定了系统能力的硬性边界，直接影响产品定位、功能设计和评测策略。以下分析基于模型能力评估和同类项目（仲景 ZhongJingGPT 用 Qwen1.5-1.8B）的调研结论。

### 13.2 能力边界评估

| 能力维度 | 能做 | 不能做 / 做不好 | 设计影响 |
|---------|------|----------------|---------|
| 知识检索增强 | RAG 上下文注入后生成准确回答 | 无 RAG 时知识幻觉严重 | 检索是必选项，不是增强项 |
| 风格迁移 | LoRA 微调后输出带口语化讲解风格（不绑定特定人物） | 长文本（>800字）风格一致性下降 | 单轮回答控制在 200-800 字 |
| 角色扮演 | 短文本内可维持简单人设 | 多轮对话中人设不可逆崩塌 | 不做显式角色扮演，只做口语化风格迁移 |
| 逻辑推理 | 单步推理（A→B）可完成 | 多步因果推理（A→B→C→D）易出错 | 复杂查询拆解为多步检索，不依赖模型推理 |
| 上下文记忆 | 单轮问答完全可用 | 超过 3-4 轮后早期信息丢失 | 默认单轮模式，多轮可选但不保证质量 |
| 生成速度 | Q4 在 2 核上 5-15 tok/s | 无法做到秒级响应 | 流式输出，25-40s/回答 |

### 13.3 口语化风格迁移

本项目选择**口语化风格迁移**方案，不做显式角色扮演，也不绑定到特定人物。

**口语化风格迁移**指通过 LoRA 微调让模型的 token 分布偏向口语化表达（如「什么意思呢」「你想想看」「就是说」），使回答不像教科书而像老师讲课。训练数据来自倪海厦讲稿（高度口语化），但目标不是"像倪海厦"，而是"不像教科书"。

**不绑定特定人物的理由：**

1. **1.5B + LoRA 的能力边界**：LoRA rank 8-16 只有 ~4-12M 可训练参数，足以做词汇分布偏移（多用口语词、短句），但不足以维持特定人物的深层风格（修辞节奏、幽默感、特定句式链）。"像倪海厦"是窄目标，1.5B LoRA 学不到深层，只会学到表面模式（偶尔蹦出口语词），效果反而不自然。口语化是宽目标，即使偶尔走偏也不违和（"老师偶尔正经一下"）。

2. **产品定位清晰度**：当前定位是「中医经典知识检索与理解助手」，核心卖点是知识检索能力和方药关联查询。SFT 的职责是风格迁移，知识由 GraphRAG 提供。绑定特定人物会让评测重心从「检索准确率」漂移到「人格一致性」。

3. **评测客观可量化**：口语化程度可用自动化指标量化——口语标记词密度（对比基座模型）、平均句长、反问/感叹句比例。不依赖人工主观打分，也不需要绑定到某个人物的原文做 embedding 对比。

### 13.4 对系统设计的约束

| 约束 | 具体措施 | 涉及模块 |
|------|---------|---------|
| 单轮为主 | API 默认不维护对话历史，每次请求独立 | FR8 Web 服务 |
| 回答长度限制 | max_tokens 设置上限，控制 200-800 字 | FR7 生成流程 |
| 检索必选 | 不允许模型无上下文「裸答」，检索为空时返回提示而非生成 | FR7 查询路由 |
| 复杂查询拆解 | 多跳关联查询由 GraphRAG 完成，不依赖模型推理 | FR6 GraphRAG |
| 风格通过微调实现 | system prompt 只写角色定位，不写「模仿XX风格」 | FR7 System Prompt |
| 评测聚焦知识准确 | 50 题评测集以知识检索/方药查询/经典解释为核心 | FR9 评测体系 |

### 13.5 模型能力提升路径

若后续资源升级（如服务器升到 8G 可跑 7B 模型），以下设计可扩展：

| 升级项 | 当前 | 升级后 | 改动范围 |
|--------|------|--------|---------|
| 显式角色扮演 | 不做 | 可加 `mode=persona` 参数 | system prompt + 路由 |
| 多轮对话 | 单轮 | 可开多轮上下文 | API 层 |
| 长文本生成 | ≤ 800 字 | ≤ 2000 字 | max_tokens |
| 复杂推理 | GraphRAG 替代 | 模型直接推理 | 生成流程 |

这些扩展点在当前架构中已预留接口，升级时不需要重构。
