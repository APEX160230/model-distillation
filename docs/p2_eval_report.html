P2.0 架构改进

核心变化：从单一向量检索升级为查询路由 + 混合检索架构

新增组件

  • QueryRouter — 正则+关键词匹配，5 种查询类型分类
  • BM25Retriever — jieba 分词 + BM25 关键词精确匹配
  • HybridRetriever — 整合路由 + BM25 + 向量 + 倒排索引，RRF 融合
  • reciprocal_rank_fusion — 多路检索结果融合算法

各路由策略

  • clause_id：正则提取 "第X条" → 直接从 330 条条文按 ID 取，O(1)，100% 准确
  • formula：72 个方剂名匹配 → 方剂数据库 clause_id 映射 → 精确取出处条文
  • herb：药材名提取 → 药材→方剂倒排索引 → 多药材取交集
  • comparison：双实体分割 → 各自走 formula/向量检索 → RRF 融合去重
  • semantic：问题词去除 → BM25 + 向量并行检索 → RRF 融合

剩余问题与下一步

经典解释 (semantic route) 是当前最弱环节：recall 33%，10 题中仅 3 题命中 reference clause

问题根因

  • "什么是太阳中风证" → 改写为 "太阳中风证" → BM25/向量仍然匹配不到 clause 12
  • 现代汉语概念（"太阳中风证"）与文言文条文（"太阳中风，阳浮而阴弱..."）语义鸿沟大
  • BM25 分词 "太阳/中风/证" 无法精确匹配条文中的 "太阳中风" 连续词

P2.1 优化方向

  • 查询改写增强：建立 "现代概念→文言关键词" 映射表（"太阳中风证" → "太阳中风 桂枝汤"）
  • GraphRAG：用药材↔方剂↔证型图谱处理多跳关系查询
  • 评测升级：加 LLM-as-judge 评分，keyword_accuracy 对解释/对比类问题不适用

结论

P2.0 混合检索架构 彻底解决了 P0/P1 的检索瓶颈。recall@5 从 5.4% 提升到 83.8%，延迟从 2.5s 降低到 1.2s，50 题评测仅需 1.3 分钟。

条文号查询、方剂查询、对比查询三类实现了 100% recall。药材关联从"完全不可用"变为"结构化精确查询"。经典解释的语义搜索是唯一剩余瓶颈，需要 P2.1 的查询改写增强和 GraphRAG 来解决。

系统已具备端侧部署条件：2 核 4G 可跑 Q4 量化模型 (~940MB)，p50 延迟 1.2s，并发锁 1。
